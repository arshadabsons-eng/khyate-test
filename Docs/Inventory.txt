# Page 3 — Inventory

---

## What This Page Does

The Inventory page is a four-tab system managing everything that can be listed, sold, or configured on the platform. Tab 1 manages raw materials (fabrics) with colors, properties, and quality tiers. Tab 2 manages the dress category tree by gender. Tab 3 manages tailor subscription plans. Tab 4 manages sizes and measurement field configuration. Each tab is fully independent with its own data, filters, and CRUD operations. The active tab persists in the URL as a query param `?tab=materials` so admins can bookmark and share specific tabs.

## Backend — All APIs Required

---

### Materials APIs

**GET /inventory/materials**
- Auth: admin JWT any role
- Query params: `search` (string), `material_type` (comma-separated enum values), `quality_tier` (affordable, premium, luxury), `gender` (male, female, both), `color_name` (string), `in_stock` (boolean), `is_active` (boolean), `price_min_fils` (number), `price_max_fils` (number), `page` (default 1), `limit` (default 24 for grid, 50 for table), `sort` (name_asc, name_desc, price_asc, price_desc, stock_asc, created_desc)
- Cache: Redis key built from all query params, TTL 2 minutes
- Response:
```
{
  data: Material[],
  total: number,
  page: number,
  limit: number,
  total_pages: number
}
```
- Query: filter on materials table with joins to material_colors and material_properties. Use PostgreSQL full-text search on `name || ' ' || material_type` for the search param. Use `@>` array operator to filter properties.

**GET /inventory/materials/:id**
- Returns single material with all colors array and all properties array and all images array
- No cache, always fresh for detail view

**POST /inventory/materials**
- Auth: super_admin or operations_admin only
- Body: Zod validated — name (required), name_ar (required), material_type (required enum), quality_tier (required enum), gender_target (required enum), price_per_meter_fils (required positive integer), minimum_order_meters (required positive number), stock_meters (required non-negative number), low_stock_threshold_meters, origin_country, care_instructions, care_instructions_ar, is_active (default true)
- After insert: insert colors into material_colors table, insert properties into material_properties table
- Write audit_log entry: action `material.create`, entity_type `material`, entity_id new id
- Invalidate Redis cache keys matching `inventory:materials:*`
- Response: created material with all relations

**PUT /inventory/materials/:id**
- Auth: super_admin or operations_admin
- Body: same as POST but all fields optional
- Partial update — only update fields that are present in the body
- Colors: receive full replacement array, delete existing colors for this material and reinsert. Same for properties.
- Write audit_log: action `material.update`, old_value and new_value as jsonb snapshots
- Invalidate Redis cache
- Response: updated material

**DELETE /inventory/materials/:id**
- Auth: super_admin only
- Check: if any active listing references this material via listing_materials table, return 409 with message "Material is used in X active listings. Deactivate instead."
- Soft delete via deleted_at timestamp
- Write audit_log: action `material.delete`
- Response: 200 success

**POST /inventory/materials/:id/duplicate**
- Auth: super_admin or operations_admin
- Creates a copy of the material with name prefixed "Copy of {name}", status set to inactive, same colors and properties
- Response: new material id and name

**POST /inventory/materials/bulk**
- Auth: super_admin or operations_admin
- Body: `{ action: 'activate' | 'deactivate', ids: string[] }`
- Validates all IDs exist and belong to non-deleted materials
- Batch update is_active field
- Write single audit_log per action with all affected IDs in entity_id as jsonb array
- Response: `{ updated_count: number }`

**POST /inventory/materials/:id/images**
- Auth: super_admin or operations_admin
- Body: `{ file_keys: string[], hero_index: number }`
- Validates each file_key exists in R2 and passed virus scan (check confirmed flag in uploads table)
- Replaces images jsonb array on material row
- Max 5 images enforced server-side
- Response: updated images array

### Material Colors Sub-resource

Colors are stored in a separate `material_colors` table: id, material_id FK, color_name, color_name_ar, hex_code, is_available, sort_order, created_at.

No separate endpoints — colors are always sent as part of the material PUT body as a full replacement array.

### Categories APIs

**GET /inventory/categories**
- Auth: admin JWT any role
- Query params: `gender` (male, female, unisex, all — default all), `include_inactive` (boolean default false)
- Response: nested tree structure
```
{
  data: [
    {
      id, name, name_ar, slug, gender, icon, sort_order, is_active, listing_count,
      children: [
        {
          id, name, name_ar, slug, gender, icon, sort_order, is_active, listing_count,
          children: [
            { id, name, name_ar, slug, is_active, listing_count }
          ]
        }
      ]
    }
  ]
}
```
- Query: single query fetching all categories ordered by sort_order, then build tree in application layer. Never do recursive SQL for a tree this shallow (max 3 levels).

**POST /inventory/categories**
- Auth: super_admin or operations_admin
- Body: name (required), name_ar (required), slug (auto-generated from name if not provided, must be unique), gender (required enum: male, female, unisex), parent_id (nullable — null means root category), icon (Tabler icon name string), sort_order (integer)
- Validate: if parent_id provided, check parent exists and is not already a level-3 category (max depth 3)
- Validate slug uniqueness across all categories
- Write audit_log
- Response: created category

**PUT /inventory/categories/:id**
- Auth: super_admin or operations_admin
- Cannot change gender if category has children with different gender
- Cannot change parent_id to create circular reference
- Validate slug uniqueness on change
- Write audit_log with old and new values
- Response: updated category

**POST /inventory/categories/reorder**
- Auth: super_admin or operations_admin
- Body: `{ updates: [{ id: string, sort_order: number }] }`
- Batch update sort_order for multiple categories in one transaction
- All must share the same parent_id (can only reorder siblings)
- Response: 200 success

**DELETE /inventory/categories/:id**
- Auth: super_admin only
- Check listing_count is 0 for this category AND all descendants
- Check no children exist — if children exist return 409 "Delete or reassign subcategories first"
- Hard delete (categories are configuration not transactional data)
- Write audit_log
- Response: 200 success

### Tailor Plans APIs

**GET /inventory/plans**
- Auth: admin JWT any role
- Response: all subscription_tiers ordered by monthly_price_fils ASC, each with `active_tailor_count` from a COUNT join on tailor_subscriptions where status=active
- No cache — plan data changes infrequently but tailor count should be live

**PUT /inventory/plans/:id**
- Auth: super_admin only
- Body: name, name_ar, monthly_price_fils, annual_price_fils, commission_rate_pct, max_active_listings (null means unlimited), max_portfolio_images, can_feature_listings, max_featured_slots, priority_dispute_handling, verified_badge, female_customer_eligible, is_active
- Validate: commission_rate_pct must be between 0 and 100
- Validate: annual_price_fils should be less than monthly_price_fils × 12 (enforce a discount)
- Write audit_log with old and new values — plan changes affect revenue so must be audited
- Do NOT automatically update existing tailor subscriptions — changes apply to new subscriptions only
- Response: updated plan

**GET /inventory/plans/analytics**
- Auth: super_admin only
- Response:
```
{
  distribution: [{ tier_id, tier_name, tailor_count, percentage }],
  mrr_fils: number,
  arr_fils: number,
  per_plan: [{ tier_id, tier_name, monthly_count, annual_count, mrr_fils }]
}
```
- Query: join tailor_subscriptions with subscription_tiers, group by tier, calculate MRR (monthly subscribers × monthly price + annual subscribers × annual price / 12)

### Size Management APIs

**GET /inventory/sizes**
- Auth: admin JWT any role
- Response: all sizes ordered by sort_order, each with `{ id, label, chest_min_cm, chest_max_cm, waist_min_cm, waist_max_cm, hips_min_cm, hips_max_cm, description, is_active, sort_order }`

**POST /inventory/sizes**
- Auth: super_admin or operations_admin
- Body: label (required unique), chest_min_cm, chest_max_cm, waist_min_cm, waist_max_cm, hips_min_cm, hips_max_cm, description, sort_order
- Write audit_log
- Response: created size

**PUT /inventory/sizes/:id**
- Auth: super_admin or operations_admin
- Partial update
- Write audit_log
- Response: updated size

**POST /inventory/sizes/reorder**
- Body: `{ updates: [{ id, sort_order }] }`
- Batch update sort_order in one transaction

**GET /inventory/measurement-fields**
- Auth: admin JWT any role
- Response: all measurement fields ordered by display_order

**PUT /inventory/measurement-fields**
- Auth: super_admin only
- Body: full replacement array of `{ id, field_name, field_name_ar, unit, is_required, display_order, description, description_ar }`
- Validate: cannot remove a field that has data in measurement_profiles — return 409 with count of affected profiles
- Upsert all rows in one transaction
- Write audit_log
- Response: updated fields array

**POST /inventory/size-guides**
- Auth: super_admin or operations_admin
- Body: `{ gender: 'male' | 'female', file_key: string }`
- Validates file_key exists and is confirmed in uploads table
- Upserts a size_guides table row (id, gender unique, file_key, uploaded_by FK, uploaded_at)
- Response: size guide record

## Database Tables Needed for Inventory Page

**materials** — id uuid PK, name varchar, name_ar varchar, material_type enum, quality_tier enum (affordable, premium, luxury), gender_target enum (male, female, both), price_per_meter_fils integer, minimum_order_meters numeric, stock_meters numeric, low_stock_threshold_meters numeric default 10, origin_country varchar, care_instructions text, care_instructions_ar text, images jsonb default '[]', is_active boolean default true, created_by FK profiles, created_at, updated_at, deleted_at

**material_colors** — id uuid PK, material_id FK materials, color_name varchar, color_name_ar varchar, hex_code char(7), is_available boolean default true, sort_order integer, created_at

**material_properties** — id uuid PK, material_id FK materials, property enum (breathable, stretchable, wrinkle_resistant, hypoallergenic, dry_clean_only, machine_washable, lightweight, heavyweight, sheer, opaque, anti_pilling, moisture_wicking), created_at

**sizes** — id uuid PK, label varchar unique, chest_min_cm numeric, chest_max_cm numeric, waist_min_cm numeric, waist_max_cm numeric, hips_min_cm numeric, hips_max_cm numeric, description text, is_active boolean default true, sort_order integer, created_at, updated_at

**measurement_fields** — id uuid PK, field_name varchar unique, field_name_ar varchar, unit enum (cm, kg), is_required boolean default false, display_order integer, description text, description_ar text, body_group enum (upper_body, mid_body, lower_body, general), created_at, updated_at

**size_guides** — id uuid PK, gender enum (male, female) unique, file_key varchar, uploaded_by FK profiles, uploaded_at timestamp

**Indexes**:
```sql
CREATE INDEX idx_materials_type ON materials(material_type) WHERE deleted_at IS NULL;
CREATE INDEX idx_materials_tier ON materials(quality_tier) WHERE deleted_at IS NULL;
CREATE INDEX idx_materials_gender ON materials(gender_target) WHERE deleted_at IS NULL;
CREATE INDEX idx_materials_active ON materials(is_active) WHERE deleted_at IS NULL;
CREATE INDEX idx_materials_fulltext ON materials USING gin(to_tsvector('english', name || ' ' || material_type));
CREATE INDEX idx_material_colors_material ON material_colors(material_id);
CREATE INDEX idx_material_properties_material ON material_properties(material_id);
CREATE INDEX idx_categories_parent ON categories(parent_id);
CREATE INDEX idx_categories_gender ON categories(gender);
CREATE INDEX idx_sizes_sort ON sizes(sort_order);
CREATE INDEX idx_measurement_fields_order ON measurement_fields(display_order);
```

**RLS on materials**: admins all. Tailors can read active non-deleted materials. Customers can read active non-deleted materials. Nobody except service role can update deleted_at directly.

**RLS on material_colors and material_properties**: same read access as parent material. Write only for admins via service role in Edge Functions.

  },
  onSettled: () => queryClient.invalidateQueries({ queryKey: ['materials'] }),

## Security

- POST, PUT, DELETE on materials, categories, plans, sizes — require super_admin or operations_admin role checked in middleware before Edge Function runs
- GET endpoints — any admin role
- Plan edits (PUT /inventory/plans/:id) — super_admin only due to financial impact
- Measurement fields configuration (PUT /inventory/measurement-fields) — super_admin only, validated server-side that no fields with existing data are removed
- All file_keys in image uploads validated server-side to belong to the authenticated user's upload session before being associated with a material
- Bulk actions validate that all provided IDs exist and are not deleted before executing — prevents ID fishing attacks
- Commission rate changes on plans are written to audit_logs with old and new values because they directly affect all future revenue calculations
- Category slug uniqueness enforced at database level with a unique index in addition to the application-level check
