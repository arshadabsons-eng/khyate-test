# Page 2 — Overview Dashboard

---

## Login Clarification (Applies to All Pages)

There is one single login page at `/login`. No separate URLs for admin, tailor, or customer staff. The email entered determines the role. After TOTP verification the backend reads the `role` field from the `profiles` table and routes accordingly: `super_admin`, `operations_admin`, `support_agent` all land on `/overview`. If a user with a non-admin role somehow hits the admin app they are rejected at the middleware level with a 403 before any page renders. Role is stored in the JWT claims so middleware can check it without a database call on every route.

---

## What This Page Does

The Overview page is the first page an admin sees after login. It gives a real-time snapshot of the entire platform: revenue, orders, tailors, disputes, and a live activity feed. It also shows a 90-day forecast. All data auto-refreshes every 5 minutes via TanStack Query's `refetchInterval`. The Supabase Realtime subscription on the activity feed updates instantly without polling.

## Backend — APIs Required

**GET /analytics/overview**

- Auth: admin JWT required, role must be super_admin or operations_admin or support_agent
- Rate limit: 60 requests per minute per admin
- Cache: Redis cache key `analytics:overview`, TTL 5 minutes, invalidated when any order status changes or new tailor registers
- Response shape:

```
{
  tailors: {
    active: number,
    inactive: number,
    pending_verification: number,
    delta_vs_yesterday: number
  },
  customers: {
    total: number,
    new_today: number,
    delta_vs_yesterday: number
  },
  orders: {
    today_count: number,
    today_gmv_fils: number,
    today_revenue_fils: number,
    delta_gmv_vs_yesterday: number,
    delta_revenue_vs_yesterday: number
  },
  disputes: {
    open_count: number,
    delta_vs_yesterday: number
  },
  pending_verifications: number,
  pending_listing_reviews: number
}
```

- Query: single SQL query using CTEs. One CTE for today's aggregates, one for yesterday's aggregates, one for tailor counts by status, one for open disputes. Return all in one response. Never make 8 separate queries for 8 KPI cards.

**GET /analytics/revenue**

- Query params: `period` (day, week, month, year), `from` (ISO date), `to` (ISO date)
- Auth: admin JWT, super_admin and operations_admin only
- Cache: Redis key `analytics:revenue:{period}:{from}:{to}`, TTL 10 minutes
- Response: array of `{ date: string, gmv_fils: number, commission_fils: number, readymade_fils: number, custom_stitch_fils: number, material_fils: number }` one object per time bucket
- Query: use `generate_series` in PostgreSQL to ensure every date bucket is present even if zero orders that day, LEFT JOIN orders on date. This prevents gaps in the chart line.

**GET /analytics/top-tailors**

- Query params: `period` (this_month, last_month, last_90_days)
- Auth: admin JWT
- Cache: Redis TTL 10 minutes
- Response: array of top 10 `{ tailor_id, name, avatar_url, city, gmv_fils, order_count, rating_avg, tier }`
- Query: aggregate orders by tailor_id for the period, join tailor_profiles, order by gmv_fils DESC, limit 10

**GET /analytics/forecast**

- Auth: super_admin only
- Cache: Redis TTL 1 hour (forecast does not need to update every 5 minutes)
- Response: array of `{ date: string, projected_gmv_fils: number, projected_revenue_fils: number, confidence: 'high' | 'medium' | 'low' }` for next 90 days
- Calculation: compute 6-month trailing daily average, apply day-of-week weighting (weekends typically higher), apply month seasonality factor derived from same month last year if data exists. Mark confidence as high if 6 months of data exists, medium if 3 months, low if less.

**Supabase Realtime subscription — activity feed**

- Subscribe to `audit_logs` table INSERT events on the client using Supabase Realtime
- RLS on audit_logs already restricts to admin roles only
- Each new INSERT event appends to the feed in the UI
- No separate API endpoint needed for the feed, Realtime handles it

**GET /analytics/order-type-breakdown**

- Query params: `from`, `to`
- Response: `{ readymade: { count, fils }, custom_stitch: { count, fils }, material: { count, fils } }`
- Cache: Redis TTL 5 minutes

## Database Queries

**Overview KPI query** — single query using CTEs:

```sql
WITH today_orders AS (
  SELECT 
    COUNT(*) as order_count,
    COALESCE(SUM(total_fils), 0) as gmv_fils,
    COALESCE(SUM(commission_fils), 0) as revenue_fils
  FROM orders
  WHERE created_at >= CURRENT_DATE
    AND status NOT IN ('cancelled', 'refunded')
),
yesterday_orders AS (
  SELECT 
    COALESCE(SUM(total_fils), 0) as gmv_fils,
    COALESCE(SUM(commission_fils), 0) as revenue_fils
  FROM orders
  WHERE created_at >= CURRENT_DATE - INTERVAL '1 day'
    AND created_at < CURRENT_DATE
    AND status NOT IN ('cancelled', 'refunded')
),
tailor_counts AS (
  SELECT
    COUNT(*) FILTER (WHERE is_active = true AND is_verified = true) as active,
    COUNT(*) FILTER (WHERE is_active = false) as inactive,
    COUNT(*) FILTER (WHERE verification_status = 'pending' OR verification_status = 'under_review') as pending
  FROM tailor_profiles
  WHERE deleted_at IS NULL
),
customer_counts AS (
  SELECT COUNT(*) as total
  FROM customer_profiles
  WHERE deleted_at IS NULL
),
dispute_counts AS (
  SELECT COUNT(*) as open_count
  FROM disputes
  WHERE status IN ('open', 'awaiting_tailor_response', 'under_review')
),
pending_listings AS (
  SELECT COUNT(*) as count
  FROM listings
  WHERE status = 'pending_review' AND deleted_at IS NULL
)
SELECT 
  tc.*,
  cc.total as customer_total,
  tod.order_count,
  tod.gmv_fils,
  tod.revenue_fils,
  yod.gmv_fils as yesterday_gmv,
  yod.revenue_fils as yesterday_revenue,
  dc.open_count as dispute_count,
  pl.count as pending_listing_count
FROM tailor_counts tc, customer_counts cc, today_orders tod, 
     yesterday_orders yod, dispute_counts dc, pending_listings pl;
```

**Revenue time series query** using generate_series to fill gaps:

```sql
SELECT 
  d.date::date,
  COALESCE(SUM(o.total_fils), 0) as gmv_fils,
  COALESCE(SUM(o.commission_fils), 0) as commission_fils,
  COALESCE(SUM(CASE WHEN o.order_type = 'readymade' THEN o.total_fils END), 0) as readymade_fils,
  COALESCE(SUM(CASE WHEN o.order_type = 'custom_stitch' THEN o.total_fils END), 0) as custom_stitch_fils,
  COALESCE(SUM(CASE WHEN o.order_type = 'material' THEN o.total_fils END), 0) as material_fils
FROM generate_series($1::date, $2::date, '1 day'::interval) AS d(date)
LEFT JOIN orders o 
  ON o.created_at::date = d.date::date
  AND o.status NOT IN ('cancelled', 'refunded')
GROUP BY d.date
ORDER BY d.date ASC;
```

## State Management

Use TanStack Query for all server state. No Redux or Zustand needed for this page.

```typescript
const { data: overview, isLoading: overviewLoading } = useQuery({
  queryKey: ['analytics', 'overview'],
  queryFn: () => apiClient.get('/analytics/overview'),
  refetchInterval: 5 * 60 * 1000,
  staleTime: 4 * 60 * 1000,
})

const [revenuePeriod, setRevenuePeriod] = useState<'day'|'week'|'month'|'year'>('month')

const { data: revenueData } = useQuery({
  queryKey: ['analytics', 'revenue', revenuePeriod],
  queryFn: () => apiClient.get('/analytics/revenue', { params: { period: revenuePeriod } }),
  staleTime: 9 * 60 * 1000,
})

const [topTailorPeriod, setTopTailorPeriod] = useState<'this_month'|'last_month'|'last_90_days'>('this_month')

const { data: topTailors } = useQuery({
  queryKey: ['analytics', 'top-tailors', topTailorPeriod],
  queryFn: () => apiClient.get('/analytics/top-tailors', { params: { period: topTailorPeriod } }),
})
```

Realtime feed uses a `useState` array capped at 50 items. Supabase Realtime channel subscribed in a `useEffect` with cleanup on unmount.

## Security

- Middleware checks JWT on every request to `/analytics/*` endpoints
- Role check: support_agent cannot access `/analytics/revenue` or `/analytics/forecast` — returns 403
- All monetary values computed server-side — client only receives fils integers and formats them for display
- Redis cache keys are not user-specific (they are platform-wide aggregates) so no risk of leaking user data through cache
- Supabase Realtime channel for audit_logs uses RLS — the subscription only receives rows that the authenticated admin is allowed to see per the RLS policy on audit_logs
